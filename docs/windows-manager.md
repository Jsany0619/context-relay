# Windows 本机任务管理器

首版用于在本机创建、管理和交接 Codex 任务。一个任务可以接续多个 App Server 会话，目标、权限、证据和执行状态保存在同一份任务记录中。现有独立技能继续保留，`install.py` 不会安装或启动管理器。

## 启动

需要 Windows、Python 3.10+（包含 Tk）和已经能正常使用的 Codex 命令及登录状态。在仓库目录运行：

```shell
python -m relay --check
python -m relay
```

也可双击仓库根目录的 `start-manager.cmd`。`--check` 检查 Python、Tk 窗口和 Codex 命令位置，不启动 App Server 或创建任务。若系统中的 `python` 不是所需版本，请用对应 Python 的完整可执行路径运行。

默认数据目录为 `%LOCALAPPDATA%\ContextRelay`；可用 `python -m relay --state-dir "完整目录路径"` 指定。状态目录与项目工作目录必须分开：不能相同，也不能任何一方包含另一方，旧任务记录同样受此检查。一个状态目录只允许一个管理器进程打开。不要为绕开已有任务归属而复制状态目录或直接修改数据库。

## 完成一项任务

1. 点击“新建任务”，填写名称、实际存在的工作目录、任务目标和完成标准。默认“只读”；需要修改工作区时选择“允许修改工作区”。Token／分钟上限可留空；自动交接默认关闭，勾选只授权这个任务。
2. 选中任务，点击“启动 / 继续”。补充指令框可留空，或填写本轮的新要求。右侧展示目标、最新回复、上下文估算、累计用量和状态。一次回复结束只表示“等待继续”，不自动宣称项目完成。
3. 出现审批时核对首屏的实际命令或文件路径，完整参数与变更可滚动查看；只能“仅此一次允许”或“拒绝”。没有完整动作资料时不能允许。普通问题按题目分别回答；秘密问题不会采集密码或密钥，应使用 Codex 原生登录。其他权限扩张请求由控制器拒绝。
4. 需要停止时点击“暂停”。出现“待核对恢复”或结果不明时先点击“核对恢复”，核实原会话和在途操作。创建、启动或外部操作结果未知时不自动重发，避免重复执行。
5. 任务空闲或暂停时可点击“预备快照”，界面显示保存时间及“仅预备，交接前须重验”；未完成在途操作或审批时不能保存。任务空闲且资料完整时可点击“交接”。正式交接的摘要和接收核验均以只读模式运行；接收方通过绑定检查点的核验后才接管，并恢复原任务的权限上限。没有进展不会连续自动创建新会话。
6. 达到原目标后点击“标记完成”。“导出”写出任务 JSON，选择尚不存在的新文件名；导出不是备份全部工作区，也不证明外部操作已经成功。

关闭窗口时，有运行中任务会提示是否中断。窗口等待管理器清理完成才退出；未能确认停止的任务保留为待核对恢复。不要将“窗口已关闭”当作所有外部副作用均已确认的证据。

启动回执到达不等于原生轮次已经开始。若立即点击“暂停”，管理器先保存“正在暂停”，等对应 `turn/started` 到达后再发一次中断；重复点击或重复通知不会重发。若完成通知先到，则保留暂停，已完成的工作轮次只记一次，不自动进入交接。“正在暂停”仍需等待实际结果，不能当作已停止。

自动交接须在新建任务时明确开启。工作轮次完成并进入空闲、遥测仍新鲜时，达到 70% 自动保存预备快照；达到 80% 且至少发生两次压缩时优先进入正式交接。数据缺失或过期不按数值触发。手动“预备快照”不要求达到阈值。这些阈值是预防策略，不代表已测得错误概率。

预备快照只收集本地已记录的要求、问题回答、最新回复、最多 20 个来源轮次引用、文件摘要值及明确未知项，不额外调用模型推理或创建会话。它不是完整决策总结或工作区备份，始终标记 `ready=false`。正式交接仍实时生成摘要、检查文件并核验 READY，不能凭已有预备快照跳过这些步骤。

## 查找、归档和操作记录

搜索框按任务名称、目标和目录查找，不区分英文字母大小写；可叠加状态筛选。筛选只改变列表展示，运行中的任务仍接收通知，关闭管理器仍会检查所有任务。没有匹配项时，详情和任务操作会清空，避免操作隐藏任务。补充指令按任务分别保留在当前窗口内，关闭窗口后不会保存这些未发送草稿。

已完成且没有待核对操作的任务可以本地归档，再从归档列表取消归档。归档不删除任务或项目文件，也不调用 Codex 原生会话归档；取消归档后仍是已完成，不自动继续、不改变权限或执行者。未知结果、待审批或仍在进行的工作不能通过归档隐藏。

“操作记录”读取该任务最近 100 条本地事件，显示在单独的只读窗口，重新打开可刷新。请求启动、收到回执、原生开始、轮次结束和用户标记完成是不同记录；列表默认不展开原始提示词、命令和回答。这不是完整聊天记录，也不是外部发布或付款成功的凭证。搜索、归档和查记录不产生模型推理用量；原有任务运行仍可能正常消耗用量。

## 权限、预算与交接边界

- **会话范围：**管理器创建独立 App Server 会话，不导入已有桌面聊天，不保证显示在官方桌面侧栏。首版仅接 Codex，没有手机控制或多工具平台能力。
- **权限：**只读或工作区可写，审批策略为按需询问；仅支持单次命令／文件批准，没有整会话放行或自动继承 full-access。交接准备不得扩大权限。
- **外部能力：**对管理器自己的会话禁用已配置的外部 MCP 服务、apps 和插件，并逐页核对所报告的 MCP 运行状态为 disabled、无可用工具；不修改全局配置，也不影响其他客户端。它不是操作系统级网络隔离；已经授权的命令仍可能产生其权限范围内的副作用。
- **预算：**Token 和分钟限制是检查点上的软边界。运行中的模型或工具调用可能超出设定上限；用量估算不是费用结算，也不是硬性计费封顶。可靠终态确认后，运行时间只结算一次；已确认暂停的时间不继续增长，结果未知的时间区间保守计入。
- **工作区检查：**交接扫描最多 4096 个文件、总计 128 MiB，超限则停止交接。排除 `.git`、`.venv`、`venv`、`node_modules`、`__pycache__`、`.codex`；Git 项目另核对 Git 目录位置、分支和 HEAD 的元数据摘要。首版拒绝扫描范围内的符号链接或链接目录，不跟随它们读取内容。
- **覆盖范围：**排除目录不在普通文件内容快照中；快照不能证明外部服务状态、未保存编辑或其他客户端的行为。新的文件变化会使旧检查点失效，需重新核验。
- **执行归属：**新旧受管会话的请求受执行者、代次和当前轮次检查约束。这个约束不锁住操作系统，也不能阻止其他应用、旧命令或不遵循协议的客户端修改同一工作区。

工作区可写任务在准备摘要和接收方 READY 核验时显示只读是正常流程。核验须回看原始用户要求、任务权限记录、检查点和原生会话实际配置；成功移交后才按原任务的权限上限继续。摘要或 READY 自称“有权限”不能替代原始记录。管理器的只读模式是执行权限上限，与独立技能所遵守的聊天 Plan／只读模式限制分别处理，不能借交接升级用户原有权限。

## 数据与恢复

管理器在状态目录保存 SQLite 任务／事件记录、预备快照和交接检查点，均为本地明文。`drafts/<task-id>.json` 每项任务只保留最新一份预备快照，再次保存会替换旧稿。不要把这个目录、导出记录或真实截图上传到公共仓库。Codex App Server 也可能按自身配置保存会话记录。

这份管理器记录与独立技能在 `CODEX_HOME/context-handoffs`（默认 `~/.codex/context-handoffs`）保存的 JSON 状态、交接包和遥测记录彼此独立。两者不会自动迁移或相互接管，不能把一边的 READY、执行者或完成状态当作另一边的确认。

敏感信息检测只是一组启发式检查，不是全面脱敏或凭据保险箱；原始资料尽量使用引用。授权记录、摘要和 READY 均需核对原始来源，不能因为一段文本来自交接包就提升为新授权。

重启后先处理“待核对恢复”。恢复必须核对已知轮次的准确 ID 和终态，以及所有已跟踪工具 ID 对应的终态；会话显示空闲本身不足以确认结果，证据缺失继续阻塞。接收核验轮次的恢复不会采纳旧 READY 或自动移交执行权。已记录但尚未发出的用户修正保留在下一次明确“启动 / 继续”的输入中，最新修正优先；已完成动作只作上下文，不要求重做。

当前版本不会盲目重试未知的创建／启动请求，不会自动抢回已经移交的执行权，也不会把旧 READY 升级成新检查点确认。自动交接的摘要请求超时时，异常处理保留最新持久化状态里的未知请求意图，不会用过期状态覆盖它。确实无法核实的情况保留阻塞，先调查原始结果。

## 验证状态

当前任务整理版本有 90 项管理器测试通过：38 项原控制器、5 项传输、22 项界面、7 项快照、12 项恢复、6 项本地任务整理。原技能 71 项运行时和 6 项安装器测试也已重新通过，共 167 项。控制器和传输使用模拟环境，界面使用实际 Tk 控件；新覆盖归档持久化、未收束状态拒绝归档、筛选隐藏任务保护、按任务保留输入、延迟回执、历史记录白名单和 96／144 DPI 等效布局。启动环境检查也通过。

另用真实 Manager 与 Tk、隔离临时数据走通搜索、归档、查询记录和取消归档，完成状态和项目文件保持不变，原生请求数为 0，测试窗口及工作线程正常关闭。这证明本地整理流程，并未重新执行原生交接或中断恢复；之前的原生证据按版本保留如下。

首版 `d6d7acf` 于 2026-09-30 在本机 Windows、Python 3.13.2、Tk 8.6.15、Codex 0.153.4 上验收，彼时 54 项管理器、原技能 71 项运行时和 6 项安装器测试全部通过。下面的两次原生交接与只读重启记录属于该首版验收；其他符合最低版本的环境尚未逐一验收。

FakeManager 的实际 Tk 窗口测试覆盖界面刷新、单次审批、普通问题回答、拒绝秘密输入、慢调用不阻塞界面，以及关闭失败保留窗口。关闭信号与控制器共享，慢创建返回后不会因下一次轮询再启动后续工作。

已用合成任务查看真实 Tk 窗口，修正默认高度与位置，确认本机缩放下审批动作、按钮和底部操作可见；另检查了 96／144 DPI 等效的 Tk 字体缩放布局，没有改动系统显示设置。截图保留在仓库外，只证明界面可见性，不作为任务执行或跨机兼容证据。

真实受控样例已通过：同一任务接续 3 个独立 App Server 会话，将 `counter.txt` 从 0 改为 1、2、3；两次交接各完成 READY 的六项核验及执行权移交，接收会话随后完成实际工作。所报告的 4 项 MCP 状态均为 disabled，工具数量均为 0。

首次原生尝试因 READY 为 false 安全停止。修正管理器协议与独立技能状态记录、只读预核验之间的歧义后，第二次独立运行通过，没有跳过 READY。成功样例全流程约 9 分 26 秒；交接会增加推理用量和等待时间，这一简单样例不能代表一般性能。

关闭原管理器后，使用同一状态目录重启的只读恢复核验已通过：仍为第 2 次移交后的执行代次，任务进入暂停状态，计数保持为 3。核验只发出 `config/read` 和 `thread/read`，没有 `turn/start`；这证明状态可读取并核对，不证明崩溃或真实中断后已能继续执行。

可靠性版本 `8e429e0` 的原生恢复验收于 2026-09-30 在 Codex 0.153.4 上通过：启动回执后立即调用暂停，由管理器等待匹配的原生 `turn/started` 后才发送中断，取得 interrupted／paused。关闭重开并只读核对后，任务与会话身份不变，执行代次仍为 0；随后明确启动一个不同 ID 的只读轮次，回复包含测试文件中的唯一字符串，文件哈希保持不变，完成工作轮次为 1，全程没有审批响应。这验证了受控只读任务的实际继续执行，不代表任意外部操作都可恢复。

同次原生运行也验证了手动预备快照：`kind=preparatory`、`ready=false`，测试文件哈希匹配；请求仅为一次 `thread/read`，没有新增 `turn/start` 或 `thread/start`。早期中断时序问题曾保留未知结果而未重试，修复后的独立运行直接覆盖产品“立即暂停”的路径，无需调用端先等待开始通知。

高上下文压力下的自动触发仍仅有模拟覆盖。物理睡眠、断电、断网、崩溃和其他环境未做原生实测。

运行当前管理器测试：

```shell
python -m unittest discover -s tests -v
```

另有明确选择执行的原生复现脚本，默认测试不会调用它们。下面是 Windows 命令提示符（cmd）的示例；每个 `--root` 都必须指定一个尚不存在、且位于仓库外的新路径。PowerShell 中可将 `%TEMP%` 换成 `$env:TEMP`。连续两次交接样例：

```shell
python tests/live_smoke.py --run --root "%TEMP%\context-relay-live-choose-new-name"
```

该脚本在独立目录中把 `counter.txt` 按三个工作轮次从 0 改为 1、2、3，中间执行两次交接。立即暂停、重启后只读恢复及手动快照样例：

```shell
python tests/live_recovery.py --help
python tests/live_recovery.py --run --root "%TEMP%\context-relay-recovery-choose-new-name"
```

不加 `--run` 只显示帮助。恢复脚本建立相互独立的 `project` 与 `state` 子目录，生成一次性测试文件，验证中断终态、重启后身份、明确继续后的实际回复及文件不变，并检查预备快照没有发起推理或建聊。

两个脚本都会消耗真实 Codex 用量并保存本地报告，不保证在所有环境无需审批就能通过；遇到待审批、待回答或无法确认的结果时安全停止，不绕过请求，也不重试未知结果。报告及会话标识仍属于本地资料，不应上传公共仓库。

独立技能的 71 项运行时测试和 6 项安装器测试仍按 README 中的原命令运行。管理器测试数量随实现变化，以实际测试输出为准。
